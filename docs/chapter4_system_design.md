# 第四章 系统总体设计

## 4.1 系统总体架构设计

### 4.1.1 微服务架构说明

传统的单体架构将所有业务逻辑耦合在一个进程中，在面对秒杀这类瞬间流量激增的场景时，存在三个核心矛盾：其一，单体应用的水平扩展粒度过粗，秒杀时真正承压的是库存扣减和订单创建逻辑，但却不得不将整个应用进行扩容；其二，单点故障的影响面过大，一个模块的异常可能导致整个系统不可用；其三，不同业务对技术栈和资源的需求差异明显，例如商品查询是读密集型操作，而下单是写密集型操作，统一的资源配置难以满足两者的最优需求。

基于上述考量，本系统采用微服务架构进行设计。整体架构遵循"网关 + 后端服务集群"的分层模式，服务间通过 RPC 进行通信，每个服务独立部署、独立扩缩容。具体而言，本系统选用字节跳动开源的 CloudWeGo 技术栈作为核心框架：HTTP 网关层采用 Hertz 框架，后端微服务间的 RPC 通信采用 Kitex 框架，服务契约通过 Thrift IDL 进行定义。之所以选择 CloudWeGo 而非传统的 gRPC + gin 方案，是因为 Kitex 在高并发场景下具有更优的性能表现——其底层网络库 Netpoll 基于 epoll 实现了高效的非阻塞 I/O 多路复用，同时 Kitex 原生支持多路复用（Mux）传输模式，能够在单连接上承载多个并发请求，有效降低连接建立的开销。

在服务治理层面，系统采用 Etcd 作为服务注册与发现中心。每个微服务在启动时向 Etcd 注册自身的网络地址，API 网关在发起 RPC 调用时通过 Etcd Resolver 动态获取目标服务的可用实例列表，并结合加权轮询（Weighted Round Robin）负载均衡策略将请求分发到不同实例上。这种设计使得服务实例的增减对调用方透明，为系统的弹性伸缩提供了基础。

之所以将系统划分为这三层，核心考量在于**关注点分离**。网关层聚焦于接入控制，不涉及业务逻辑，因此可以独立进行限流策略的调整而不影响业务代码；业务服务层的每个服务只关注自己的领域逻辑，商品服务不需要了解订单的状态机，订单服务也不需要知道库存在 Redis 中如何存储；数据层则提供统一的存储和消息传递能力，与业务逻辑解耦。

## 4.2 系统模块划分

### 4.2.1 网关服务（API Gateway）

网关服务是整个系统的统一入口，基于 Hertz HTTP 框架实现。选择专设网关层而非让客户端直连后端服务，原因有三：

第一，**协议转换**。客户端使用 HTTP/JSON 协议进行通信，而后端微服务间使用 Thrift 二进制协议进行 RPC 调用。网关承担了两种协议之间的桥接职责——接收 HTTP 请求、解析参数、调用对应的 RPC 服务、将 Thrift 响应转换为 JSON 返回给客户端。

第二，**横切关注点的统一处理**。身份认证、请求限流、响应压缩、异常恢复等逻辑如果分散到每个微服务中实现，不仅造成代码重复，更带来维护上的困难。本系统在网关层以 Hertz 中间件链的形式实现了这些能力：

- **JWT 认证中间件**：对需要登录态的接口（如秒杀下单、订单操作）进行 Token 校验，未通过校验的请求直接在网关层拦截，避免无效请求穿透到后端服务；
- **Sentinel 限流中间件**：基于阿里巴巴 Sentinel 框架实现流量控制，当请求速率超过预设阈值时，直接返回限流响应，保护后端服务不被突发流量打垮；
- **Gzip 压缩中间件**：对响应体进行压缩，降低网络传输量；
- **Recovery 中间件**：捕获处理过程中的 panic 异常，防止单个请求的异常导致整个进程崩溃。

第三，**路由聚合**。网关将所有外部可访问的 API 统一收敛到 `/seckill/` 路径前缀下，按业务域划分为用户（`/user/`）、商品（`/product/`）、活动（`/activity/`）、秒杀（`/action/`）、订单（`/order/`）五组路由，并通过中间件精确控制每组路由的访问权限——商品列表和活动列表允许匿名访问，而下单和订单操作则要求登录认证。

### 4.2.2 商品服务（Product Service）

商品服务负责商品信息管理和秒杀活动管理两大领域。之所以将秒杀活动的管理纳入商品服务而非独立为秒杀服务，是因为秒杀活动与商品之间存在强关联的领域关系——每个秒杀活动必然对应一个商品，活动的库存本质上是商品库存的一个子集。将二者放在同一服务中，可以在库存扣减时避免跨服务的分布式事务。

商品服务的核心职责包括：

- **商品 CRUD**：提供商品的创建、查询和列表功能，支持按分类筛选和分页查询；
- **秒杀活动管理**：创建秒杀活动时，将活动库存从 MySQL 预热到 Redis 中，为后续的高并发库存扣减做准备；
- **库存扣减**：通过 Redis Lua 脚本实现原子化的库存判断和扣减操作，扣减成功后异步同步到 MySQL，这是整个秒杀系统中并发压力最大的环节，将在 4.3 节详细阐述。

数据库层面，商品服务管理 `product` 和 `seckill_activity` 两张表，两者通过外键 `product_id` 关联。`seckill_activity` 表设计了 `start_time`、`end_time` 时间窗口字段和 `status` 状态字段，并建立了联合索引 `idx_time`，以支持按时间范围高效查询当前进行中的活动。

### 4.2.3 订单服务（Order Service）

订单服务是秒杀系统的核心枢纽，承担秒杀下单的完整业务编排和订单全生命周期管理。之所以将秒杀下单的编排逻辑放在订单服务而非网关层，是因为下单是一个涉及多步骤的业务事务（防重 → 校验 → 扣库存 → 建单 → 异步通知），这些步骤之间存在严格的顺序依赖和失败回滚逻辑，属于业务层的关注点，不应泄漏到网关层。

订单服务的秒杀下单流程设计为五个步骤：

1. **Redis SetNX 防重复下单**：利用 Redis 的 SetNX 原子操作，以 `seckill:order:{activityId}:{userId}` 为 Key 进行去重判断，确保同一用户对同一活动只能下单一次；
2. **RPC 查询活动状态**：调用商品服务获取活动详情，校验当前时间是否在活动时间窗口内；
3. **RPC 调用库存扣减**：调用商品服务的库存扣减接口，在 Redis 层完成原子扣减；
4. **创建订单记录**：库存扣减成功后，使用 Snowflake 算法生成分布式唯一订单号，将订单写入 MySQL；
5. **MQ 异步通知**：将订单消息发送到 RabbitMQ 队列，由消费者异步处理后续逻辑。

在任一步骤失败时，系统会清除 Redis 中的防重标记，允许用户重试。这种设计保证了幂等性——即使网络抖动导致客户端重复提交，也不会产生重复订单。

订单的生命周期状态包括：待支付（Pending）→ 已支付（Paid）/ 已取消（Cancelled）/ 已过期（Expired），订单表通过 `status` 字段和 `idx_status` 索引支持按状态查询。

### 4.2.4 用户服务（User Service）

用户服务负责用户注册、登录和用户信息查询。该服务的设计相对简单，但承担着整个系统的身份认证基础——用户登录成功后签发 JWT Token，后续所有需要身份标识的请求都通过该 Token 进行鉴权。

用户密码采用 bcrypt 算法进行单向哈希存储，即使数据库泄露也无法还原原始密码。用户 ID 从 10000 开始自增，通过 Snowflake 算法保证分布式环境下的唯一性。

## 4.3 高并发处理方案设计

秒杀场景的核心挑战在于：在极短的时间窗口内（通常为秒级），系统需要承受远超日常流量数十甚至数百倍的请求冲击，而可售库存往往是有限的（例如 100 件商品面对 10 万次请求）。如果所有请求都直达数据库进行库存扣减，数据库必然成为瓶颈导致系统崩溃。因此，高并发处理的核心思路是**尽早拦截无效请求、将热点操作从数据库转移到缓存**。

### 4.3.1 动静分离

在本系统的路由设计中，商品列表（`GET /seckill/product/list/`）、商品详情（`GET /seckill/product/detail/`）、活动列表（`GET /seckill/activity/list/`）等查询接口被设计为无需认证即可访问。这种设计不仅出于业务考量（允许用户浏览商品），更是高并发处理的第一层优化——这些读接口的响应结果在短时间内不会变化，可以在前端或 CDN 层进行缓存，从而将大量读请求拦截在系统外部，不产生对后端服务的调用。

而秒杀下单（`POST /seckill/action/`）等写接口则要求强制认证，且每个请求都需要经过完整的业务逻辑处理。通过这种动静分离的策略，系统将有限的后端处理能力集中用于处理真正需要写入的请求。

### 4.3.2 Redis 预扣库存

库存扣减是秒杀系统中并发冲突最为严重的操作。传统的数据库方案（`UPDATE SET stock = stock - 1 WHERE stock > 0`）在高并发下会导致大量行锁竞争，数据库的吞吐量急剧下降。本系统采用"Redis 预扣库存 + MySQL 异步同步"的两阶段方案来解决这一问题。

**第一阶段：Redis Lua 原子扣减**。在秒杀活动创建时，商品服务将活动库存通过 `WarmUpSeckillStock` 函数预热到 Redis 中，Key 为 `seckill:stock:{activityId}`。当扣库存请求到达时，通过如下 Lua 脚本在 Redis 端完成原子化的"判断并扣减"操作：

```lua
local stock = tonumber(redis.call('get', KEYS[1]))
if stock and stock > 0 then
    redis.call('decr', KEYS[1])
    return 1
end
return 0
```

选择 Lua 脚本而非 Redis 的 DECR 命令，是因为单独的 DECR 无法在一个原子步骤内同时完成"判断库存是否大于零"和"执行扣减"两个操作。如果先 GET 判断再 DECR 扣减，在两个命令之间存在并发窗口，可能导致库存扣为负数（即超卖）。而 Lua 脚本在 Redis 中是原子执行的，从根本上杜绝了超卖的可能。

**第二阶段：MySQL 异步同步**。Redis 扣减成功后，商品服务调用 `db.DeductStock` 将扣减同步到 MySQL。MySQL 中的库存作为最终的持久化记录，即使 Redis 因故障丢失数据，也可以从 MySQL 恢复。

这种方案的核心价值在于将高并发的热点操作从磁盘 I/O 密集的 MySQL 转移到了内存操作的 Redis 上。Redis 的单线程模型天然避免了锁竞争，单实例即可支撑数万 QPS 的库存扣减操作，相比 MySQL 有数量级的性能提升。

### 4.3.3 请求限流设计

即使有 Redis 预扣库存的优化，系统仍需防范超出承载能力的异常流量（如恶意刷接口、爬虫攻击等）。本系统在 API 网关层集成了阿里巴巴开源的 Sentinel 框架进行流量控制。

Sentinel 的限流规则通过 `flow.Rule` 进行配置，支持 QPS 维度的流量控制和直接拒绝（Reject）的控制行为。当某个时间窗口内的请求量超过设定阈值时，超出的请求将被直接拒绝并返回"too many request"的提示，不会进入后端业务逻辑。这种在入口处的"快速失败"策略，避免了过载请求消耗后端服务的线程和连接资源。

除了 Sentinel 的显式限流，系统还在多个层面实现了隐式的流量削减：

- **Kitex 连接限制**：每个微服务在启动时通过 `server.WithLimit` 设定了最大连接数（MaxConnections = 1000）和最大 QPS（MaxQPS = 100）的上限；
- **Redis SetNX 防重**：同一用户对同一活动的重复请求在 Redis 层即被拦截，不会穿透到库存扣减和数据库写入环节；
- **RabbitMQ 削峰填谷**：秒杀成功后的消息通过消息队列异步处理，即使瞬间产生大量订单，消费者也可以按照自身处理能力匀速消费，避免下游服务被峰值流量击溃。

## 4.4 数据存储与一致性设计

### 4.4.1 Redis + MySQL 协同设计

本系统中 Redis 和 MySQL 各自承担不同的职责，二者的协同关系可以概括为"Redis 做决策，MySQL 做记录"。

在秒杀场景中，Redis 承担两项核心职能：一是通过 Lua 脚本实现高性能的库存扣减决策——请求是否可以成功下单，由 Redis 在微秒级完成判断；二是通过 SetNX 实现防重复下单判断——同一用户是否已经参与过秒杀，同样由 Redis 在内存中完成校验。

MySQL 则承担持久化存储的职责，是所有业务数据的最终归宿。商品信息、秒杀活动详情、订单记录等数据均以 MySQL 为准。Redis 中的数据本质上是 MySQL 数据的"热副本"——它们的存在是为了在高并发时替代 MySQL 承受读写压力，但不取代 MySQL 作为数据权威来源的地位。

之所以采用这种双存储协同的方案，而非仅使用 MySQL 或仅使用 Redis，是基于两者各自的特点做出的权衡：MySQL 提供了 ACID 事务和持久化保障，但在高并发写场景下的吞吐量有限（受磁盘 I/O 和行锁制约）；Redis 提供了极高的读写性能（基于内存操作，单线程无锁竞争），但不具备复杂事务能力且存在数据易失性风险。二者协同可以取长补短，既保证了性能又保证了数据安全。

### 4.4.2 事务处理与最终一致性

在分布式系统中追求强一致性（即所有节点在任一时刻看到的数据完全相同）的代价极高，通常需要引入两阶段提交（2PC）或 TCC 等分布式事务协议，这不仅增加了系统复杂性，更会因为锁等待和协调开销而严重降低吞吐量。对于秒杀系统而言，吞吐量是第一优先级，因此本系统采用**最终一致性**作为数据一致性策略。

所谓最终一致性，是指系统不保证在任一时刻所有组件的数据完全一致，但保证在经过一段时间后，所有数据将达到一致状态。具体到本系统的实现：

**Redis 与 MySQL 之间的库存一致性**：Redis 中的库存扣减和 MySQL 中的库存更新是分两步完成的。在极端情况下（如 Redis 扣减成功但 MySQL 更新失败），可能出现短暂的不一致窗口。系统通过两种机制保障最终一致：一是在 MySQL 更新失败时返回错误，触发上层的补偿逻辑；二是可以通过定时对账任务比对 Redis 和 MySQL 的库存差异，进行修正。

**订单创建与消息通知之间的一致性**：订单写入 MySQL 成功后，系统将消息发送到 RabbitMQ。即使消息发送失败（返回值被忽略），也不影响订单的有效性——订单已经持久化在 MySQL 中，消息队列中的消费者仅负责后续的通知和状态流转等非关键路径操作。这种"先写库再发消息"的模式，将 MySQL 作为数据的唯一可信源，MQ 仅作为异步通知渠道，从架构层面避免了分布式事务的引入。

**防重标记的一致性**：Redis 中的防重标记（SetNX）设置了 24 小时的过期时间。当下单流程中任一步骤失败时，系统会主动清除该标记（`RemoveSeckillRepeatFlag`），允许用户重试。即使因为网络异常导致标记未被清除，24 小时后标记也会自动过期，保证了系统不会永久性地阻止用户下单。

选择最终一致性而非强一致性，本质上是在 CAP 定理框架下的取舍：在网络分区（P）不可避免的前提下，秒杀系统优先保证可用性（A）——宁可在极端情况下出现短暂的数据不一致（后续可修复），也不能因为等待一致性协调而让大量用户请求超时或失败。

## 4.5 系统监控与可观测性设计

### 4.5.1 为什么需要监控

微服务架构在带来灵活性的同时，也显著增加了系统的运维复杂度。在单体架构中，一个请求的完整处理路径在同一个进程内，通过日志和调试器即可追踪问题。而在本系统中，一次秒杀下单请求需要经过 API 网关 → 订单服务 → 商品服务的多级调用链，涉及 Redis、MySQL、RabbitMQ 三种中间件的交互——当出现性能劣化或请求失败时，问题可能发生在任何一个环节。

此外，秒杀场景的流量具有高度的突发性和不可预测性。活动开始前系统可能近乎空闲，而活动开始的瞬间流量可能飙升数百倍。如果没有实时的监控手段，运维人员无法及时感知系统是否接近承载极限，更无法在问题恶化为全面故障之前进行干预（如动态扩容、降级限流等）。

因此，完善的监控体系不是系统的"锦上添花"，而是保障秒杀系统稳定运行的必要条件。

### 4.5.2 监控指标设计

本系统的监控指标围绕"RED 方法论"（Rate、Errors、Duration）进行设计，覆盖三个层面：

**请求层指标**：
- **QPS（每秒请求数）**：反映系统的实时吞吐量。在秒杀场景中，QPS 是判断流量是否达到预期峰值、限流策略是否生效的关键依据。通过 Prometheus 的 `rate()` 函数对请求计数器求导即可获得；
- **响应时间（P50/P95/P99）**：反映系统的延迟水平。秒杀场景下用户对延迟极为敏感，P99 响应时间超过阈值通常意味着系统出现了资源竞争或下游服务劣化；
- **错误率**：HTTP 5xx 响应的比例。错误率突增通常预示着系统某个环节出现了故障，需要立即排查。

**资源层指标**：
- **Redis 指标**：通过 Redis Exporter 采集连接数、内存使用率、命中率、每秒操作数等。库存预热后 Redis 的内存使用量和 QPS 是重点关注对象；
- **MySQL 指标**：通过 MySQL Exporter 采集连接数、慢查询数、QPS 等。在秒杀期间如果 MySQL 慢查询数激增，说明数据库成为了瓶颈；
- **容器指标**：通过 cAdvisor 采集各微服务容器的 CPU、内存、网络 I/O 等。容器的 CPU 使用率接近上限时需要触发扩容。

**基础设施指标**：
- 通过 Node Exporter 采集宿主机级别的 CPU、内存、磁盘 I/O、网络带宽等指标，作为容量规划和异常排查的基础数据。

### 4.5.3 技术选型：Prometheus + Grafana

本系统选择 Prometheus 作为指标采集与存储引擎，Grafana 作为可视化展示平台，二者组合是目前云原生领域最主流的监控方案。选择这一方案而非 Zabbix、Datadog 等替代方案，基于以下几点考量：

第一，**Pull 模型与服务发现的天然契合**。Prometheus 采用主动拉取（Pull）模式采集指标——由 Prometheus Server 周期性地向各 Exporter 端点发起 HTTP 请求获取指标数据。这种模式的优势在于，被监控方无需关心监控系统的地址和可用性，只需暴露一个 `/metrics` 端点即可。在本系统的 docker-compose 环境中，Prometheus 的采集配置（`prometheus.yml`）以 15 秒为间隔，分别从 cAdvisor、Node Exporter、Redis Exporter、MySQL Exporter 四个数据源拉取指标。

第二，**强大的时序查询语言 PromQL**。Prometheus 内置的 PromQL 支持对时序数据进行聚合、过滤、函数运算等操作，可以灵活地定义告警规则和仪表盘查询。例如，通过 `rate(http_requests_total[5m])` 可以计算过去5分钟的平均 QPS，通过 `histogram_quantile(0.99, rate(http_request_duration_seconds_bucket[5m]))` 可以计算 P99 延迟。

第三，**Grafana 的可视化能力**。Grafana 支持将 Prometheus 作为数据源，通过丰富的图表类型（折线图、热力图、柱状图、仪表盘等）将监控数据以直观的方式呈现。同时 Grafana 社区提供了大量开箱即用的 Dashboard 模板（如 Node Exporter Dashboard、Redis Dashboard、MySQL Overview 等），可以快速搭建起覆盖全面的监控大盘，大幅降低了可视化的配置成本。

第四，**与现有技术栈的兼容性**。Prometheus + Grafana 均以 Docker 容器形式部署，与本系统的容器化部署方案完全一致，不引入额外的部署复杂度。同时，系统中已有的 Jaeger（链路追踪）和 Elasticsearch + Kibana（日志系统）与 Prometheus + Grafana（指标监控）共同构成了可观测性的三大支柱——Traces、Logs、Metrics，形成了完整的可观测性体系。

## 4.6 本章小结

本章从系统总体架构、模块划分、高并发处理、数据一致性和监控可观测性五个维度，对电商秒杀系统的设计方案进行了详细阐述。

在架构层面，系统采用微服务架构将业务拆分为网关、用户、商品、订单四个独立服务，以 Kitex RPC 框架为通信基础，以 Etcd 为服务注册发现中心。这种设计的核心价值在于：每个服务可以根据自身的负载特点独立扩缩容——秒杀高峰期可以单独增加商品服务和订单服务的实例数，而不需要等比例扩展用户服务。

在高并发处理层面，系统通过"漏斗型"的多级过滤策略逐层削减请求：Sentinel 限流在网关层拦截超限流量 → Redis SetNX 在订单服务层过滤重复请求 → Redis Lua 脚本在商品服务层原子扣减库存 → RabbitMQ 在订单落库后异步处理后续流程。每一层都将无效或重复的请求尽早拦截，确保最终到达 MySQL 的写操作控制在系统可承受的范围内。

在数据一致性层面，系统放弃了代价高昂的强一致性方案，转而采用最终一致性策略。Redis 负责高频决策（库存扣减、防重判断），MySQL 负责数据持久化，RabbitMQ 负责异步解耦。三者之间通过补偿机制和过期策略保障数据最终收敛到一致状态。这种设计是在吞吐量与一致性之间做出的务实权衡——对于秒杀系统而言，让尽可能多的合法请求在毫秒级内得到响应，远比保证每一毫秒的绝对一致更有业务价值。

在监控可观测性层面，Prometheus + Grafana 的指标监控、Jaeger 的分布式链路追踪、Elasticsearch + Kibana 的日志收集共同构成了"Metrics-Traces-Logs"三位一体的可观测性体系，为系统的稳定运行和故障排查提供了全方位的数据支撑。
